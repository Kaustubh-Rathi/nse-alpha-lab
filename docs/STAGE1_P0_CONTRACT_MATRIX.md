## 2. Status vocabulary and authorization mapping

The seven statuses are used exactly as written. Component status and contract status are separate; a component is never promoted by assertion.

| Status | Meaning | Authorization effect |
|---|---|---|
| `COMPONENT_IMPLEMENTED` | Code exists and its component tests may pass, but there is no independent HEAD verification of the named component or its contract scope is only a primitive | **No authorization.** Evidence only. |
| `COMPONENT_VERIFIED` | Named component tests pass at the tested revision under independent execution (E2/E3); no claim about the whole contract | **No authorization.** Supports a contract assessment. |
| `CONTRACT_PARTIAL` | At least one contract clause is independently proven; at least one material clause is missing, unproven or qualified | **No authorization.** Line blocks the batch. |
| `CONTRACT_PASS` | Every clause of this contract is independently proven at the tested revision, no open finding is charged to it, and the proof is contract-level, not merely component-level | **Authorizes this contract line only.** Migration still requires all 29 rows PASS plus gate controls. |
| `CONTRACT_NOT_IMPLEMENTED` | No implementation, or only a stub/primitive that cannot satisfy the contract | **Blocks.** |
| `CONTRACT_FAIL` | An implementation exists but a confirmed defect or contradiction violates the contract | **Blocks.** |
| `CONTRACT_BLOCKED` | The contract cannot be verified because required external evidence, a prerequisite contract or an owner decision is absent | **Blocks.** Distinct from "not implemented": code may exist, but proof is impossible at HEAD. |

**Gate status values.** `CLOSED` means the line does not open the batch gate and the next action is in-repo implementation or remediation, including resolution of any named non-passing dependency. `BLOCKED` is a stronger closure: the line cannot be entered or assessed until authoritative external evidence or an owner decision exists. `NOT APPLICABLE TO STAGE-1 BATCHES` is reserved for the legacy P0-1..P0-5 and is never counted. For a `CONTRACT_PASS` row, `CLOSED` means the row is satisfied but the batch gate remains closed; no Stage-1 batch is open at HEAD.

**Rules.**
1. **R1 — Component != contract.** `COMPONENT_VERIFIED` never promotes a row; only clause-level proof does.
2. **R2 — No PASS by existence.** A module, a passing component suite or a report `PASS` cannot create `CONTRACT_PASS`.
3. **R3 — Revision binding.** `CONTRACT_PASS` must rest on HEAD-specific proof. E0/E1 are baseline-only and cannot create or retain it.
4. **R4 — One non-PASS blocks.** The batch gate requires 29/29 `CONTRACT_PASS`; one `CONTRACT_PARTIAL`, `CONTRACT_FAIL`, `CONTRACT_BLOCKED` or `CONTRACT_NOT_IMPLEMENTED` keeps it closed.
5. **R5 — Finding charging.** A confirmed defect is charged to the narrowest contract whose named scope it violates; cross-cutting findings are listed in §7.3 so they are not lost.
6. **R6 — Specification silence.** Where no economic rule exists, the row says `SPEC GAP` and cites the decision-register entry; even a planning-final recommendation is not implementation authorization until it is approved and implemented.
7. **R7 — Legacy exclusion.** The legacy P0-1..P0-5 are downstream-only and cannot be used to claim Stage-1 completion.
